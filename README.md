# Building a SOC + Honeynet in Azure (Live Traffic)

![Building a SOC + Honeynet in Azure Live Traffic](YOUR_IMAGE_URL_HERE)
## Introduction

In this project, I constructed a miniature honeynet in Microsoft Azure to capture and analyze real-world cyber attack traffic. System and security logs were aggregated from multiple sources into a **Log Analytics Workspace**, where **Microsoft Sentinel** was configured to generate attack maps, trigger security alerts, and create incidents.

To evaluate the impact of security hardening, metrics were measured across two distinct phases:
1. **Insecure State (24-Hour Baseline):** Resources were exposed directly to the public internet with permissive firewall rules.
2. **Hardened State (24-Hour Post-Remediation):** Security controls (NSG rules, Private Endpoints, and internal firewalls) were implemented to restrict access strictly to admin traffic.

### Metrics Tracked:
- **`SecurityEvent`**: Windows Security Event logs (RDP/Kerberos/Local Authentication)
- **`Syslog`**: Linux System logs (SSH Authentication)
- **`SecurityAlert`**: Alerts triggered by Log Analytics / Microsoft Defender for Cloud
- **`SecurityIncident`**: Security incidents generated by Microsoft Sentinel
- **`AzureNetworkAnalytics_CL`**: Allowed malicious network traffic flows into the honeynet

## Network Architecture

### Architecture Before Hardening (Insecure)
![Insecure Architecture](https://github.com/touresidimohamed7/Azure-SOC/assets/152078244/6ea88b84-06ec-4a7e-9c27-dd726c041ad8)

In the initial deployment, all resources were provisioned with public endpoints accessible directly from the internet:
- **Virtual Machines (2x Windows, 1x Linux):** Built-in firewalls and Network Security Groups (NSGs) set to allow `ANY` inbound traffic (`*`).
- **Storage Account & Azure Key Vault:** Deployed with public endpoints enabled and no restriction policies.

### Architecture After Hardening (Secured)
![Hardened Architecture](https://github.com/touresidimohamed7/Azure-SOC/assets/152078244/4ec29d01-0eb9-43d0-83db-a067dd711b02)

To secure the environment:
- **Network Security Groups (NSGs):** Re-configured with a strict `Deny-All` inbound rule, allowing access **only** from the designated admin workstation IP address.
- **Resource Firewalls & Private Endpoints:** Enabled built-in host firewalls and routed Azure Storage and Key Vault traffic through **Private Endpoints** to remove public internet exposure.

## Metric Analysis & Key Takeaways

1. **Elimination of Threat Activity:** Applying strict NSG rules and Private Endpoints completely mitigated external brute-force attacks and port scans (`Syslog` dropped by 99%, while `SecurityAlert`, `SecurityIncident`, and `AzureNetworkAnalytics_CL` dropped to zero).
2. **Understanding `SecurityEvent` Spike:** While external attacks stopped, internal `SecurityEvent` counts increased. This is standard operational behavior resulting from active Log Analytics agent synchronization, internal OS auditing policies, and administrative maintenance actions performed during the hardening phase.

## Conclusion

This project successfully demonstrates how deploying defense-in-depth controls—such as Network Security Groups, host-level firewalls, and Private Endpoints—effectively closes exposure windows on public cloud infrastructure. Microsoft Sentinel provided clear visibility throughout both phases, proving invaluable for real-time monitoring, incident detection, and validating security posture improvements.
